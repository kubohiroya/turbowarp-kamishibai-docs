# 1. ワークショップの概要

## 1.1 基本情報

| 項目       | 内容                                                       |
| ---------- | ---------------------------------------------------------- |
| 題材       | 真間の手児奈（市川市国府台・真間地域の伝説、『万葉集』）   |
| 対象       | 高校生                                                     |
| 所要時間   | 40分（休憩なし）                                           |
| 参加単位   | 2人1組、1人1台                                             |
| 開催日     | 【要確定】                                                 |
| 会場       | 【要確定】                                                 |
| 定員       | 【要確定】                                                 |
| 使用DSL    | DSL 4.0系（ブロック台本、App 4.0.1）                       |

## 1.2 到達目標

参加者が40分で到達する状態を、次のとおり設定します。

1. 自分のポーズを学習させた機械学習モデルを作り、クラウドに公開できた
2. 公開したモデルのURLを、別のアプリ（紙芝居）の台本から参照できた
3. ブロック台本の決まった場所に、決まった形式でデータを入力し、作品を動かせた
4. エラー表示を読み、原因の箇所を特定して修正できた
5. 伝説を題材にした表現について、自分の考えを持てた

## 1.3 8月1日版（親子・小学生向け）からの変更点

40分枠に収めるため、次の変更を行っています。

| 観点             | 2026-08-01版                              | 本ワークショップ                                   |
| ---------------- | ----------------------------------------- | -------------------------------------------------- |
| 生成AIでの作画   | 実習に含む（約30分、保護者が操作）        | **実習から外す**（事前生成の求婚者カタログを使用） |
| ポーズのクラス数 | 2〜4（`p1`〜`p4`）                        | **2固定**（`kime`／`neutral`）                     |
| 台本形式         | YAML台本（行頭の`#`を外す）               | ブロック台本（TurboWarp-Plus-Editor）              |
| 台本の編集量     | モデルURL・asset・action（3か所）         | モデルURL・一覧の1行・scene（3か所）               |
| 休憩             | 10分                                      | なし                                               |
| 保護者の役割     | 生成AI操作、撮影オペレーター              | なし（2人1組で相互に撮影）                         |

> ⭐️ 生成AIでの作画を実習に戻す場合、40分では収まりません。最低90分枠が必要です。

# 3. 会場レイアウト

【要確定：会場見取り図】

レイアウト設計の条件を記します。

* 参加者の**背後に2m程度の空間**を確保する（ポーズを取るため）

## 4.3 遅延時の切り詰め方

12分区間が押した場合、次の順で切り詰めます。

1. **5章の動作確認を省略**し、6.1の連結再生で自分の場面を見てもらう
2. **3.5のモデル確認を省略**し、Previewでのチェックをスタッフが代行する
3. **2章を短縮**し、求婚者を番号で割り当てる（1番から順に配る）

**切り詰めてはいけない箇所**

* 0.4の題材の扱い（全員が断られる設計の説明）
* 3.6のエクスポートURLの記録（ここを飛ばすと4章が成立しない）

# 6. 事前準備内容

1. PCの電源を入れる
2. USBカメラを接続し、認識を確認する
3. 【要確定：アカウント方式】に従ってログオンする
4. ログオン後に開く不要な画面を閉じる
5. エクスプローラーの「表示」→「ファイル名拡張子」にチェックを入れる
6. ブラウザを起動する
7. 配布URLからZIPファイルをダウンロードし、展開してデスクトップに「tekona」フォルダを配置する
8. 参加者向け資料PDFを開く
9. Teachable Machineのポーズプロジェクト（https://teachablemachine.withgoogle.com/train/pose ）を別タブで開いておく
10. 手児奈ベース作品をTurboWarp-Plus-Editorで開く**リンクのタブ**を用意しておく（読み込みに時間がかかるため）
11. カメラの画角を確認し、着席した参加者の全身（または上半身）が映る向きに調整する
12. 背後に他の参加者が映り込まないか、実際に立って確認する
13. 完成見本（`tekona-complete-sample.sb3`）が再生できることを1台で確認する
14. **当日のネットワークで、Teachable Machineの「Upload my model」が通ることを確認する**

> ⭐️ 手順14は、準備作業の中で最も重要です。会場のネットワークがアップロードを遮断する環境では、このワークショップは実施できません。代替案は8.5を参照してください。

# 7. 高校生向けの進行上の注意

## 7.1 題材の扱い

手児奈の伝説は、**入水という結末を持つ物語**です。参加者向け資料0.4で扱いを明示していますが、
口頭でも冒頭に伝えてください。

* 伝説の結末を興味本位に強調しない
* 手児奈霊神堂が現在も信仰の場であることを伝える
* 伝説の人物を題材にした創作であることを明確にする

参加者から「なぜ死んでしまうのか」という質問が出た場合は、
『万葉集』に歌われた伝説としてそう伝えられている、と事実として答えてください。
解釈を断定せず、6.3の問いにつなげてください。

## 7.2 「断られる」体験のケア

この作品は、**設計上、全員の求婚者が断られます**。

* 開始時に、**全員が断られる設計であること**と、**その理由（伝説の筋書き）**を必ず先に伝える
* 「出来が悪いから断られた」と受け取る参加者がいないか、5章で表情を見る
* 断りのセリフに、個人を否定する表現を入れない（ベース台本側で担保済み）

参加者が考えた名乗りのセリフが、相手を見下す内容・しつこく迫る内容になっていた場合は、
巡回時に書き直しを促してください。参加者向け資料2.2に注意書きがあります。

## 7.3 カメラと肖像

* カメラ映像が保存されないことを明示する（参加者向け資料0.4・1.5）
* **他の参加者を撮影しない／画面を撮影してSNSに投稿しない**ことを冒頭で伝える
* カメラに他の参加者が映り込まない配置を、事前準備で担保する

## 7.4 生成AIについて

高校生は、M365 Copilotの利用対象年齢（13歳以上）を満たします。
ただし40分枠では画像生成を実習に含めないため、当日の生成AI操作は発生しません。

発展課題として案内する場合は、次の点を伝えてください。

* 実在の人物に似せた画像を作らない
* 生成した画像の権利関係と、公開時の注意
* 生成結果が事実とは限らないこと

## 7.5 機械学習の説明の深さ

高校生向けなので、「例を見せると規則を見つける」という説明に加え、
次のどれかを**1分以内**で補足できると理解が深まります。参加者の反応を見て選んでください。

* `neutral`クラスの役割（「それ以外」を教えないと何でも`kime`になる）
* サンプルを少し動かしながら撮る理由（学習データの多様性）
* 「Preview」での確認が、テストデータによる評価に相当すること

時間が押している場合は省略してかまいません。

# 8. トラブルシューティング

参加者の画面を確認し、作業がうまく進んでいない場合は声をかけ、スタッフが対応することを伝えてください。

## 8.1 Teachable Machineでの撮影・学習

| 症状                               | 対処                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------- |
| カメラが選べない／映らない         | ブラウザのカメラ許可を確認。複数カメラがある場合はプルダウンで切り替え |
| 全身が映らない                     | 上半身だけで続行してよい。ただし`kime`／`neutral`の両方を同じ画角で撮る |
| どちらのポーズでも`kime`が高い     | `neutral`のサンプルを追加（別の立ち方・座る姿・歩く姿）して再トレーニング |
| 決めポーズで`kime`が上がらない     | 決めポーズをより大きな形に変更し、`kime`を撮り直す                     |
| トレーニングが終わらない           | タブを切り替えていないか確認。切り替えていた場合は再トレーニング        |
| 他の参加者が映り込んで学習した     | 映り込んだ側のサンプルを削除し、画角を直して撮り直す                   |

## 8.2 モデルのエクスポート

| 症状                                   | 対処                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------- |
| 「Upload my model」が終わらない        | ネットワーク混雑。1〜2分待つ。繰り返す場合は8.5の救済へ                    |
| URLをメモし忘れてタブを閉じた          | モデルは再トレーニングが必要。8.5の救済用モデルURLを配布する               |
| URLの末尾の`/`が抜けている             | 末尾に`/`を付ける。参加者向け資料3.6の注意書きを示す                       |
| `model.json`のURLを控えてしまった      | ディレクトリURL（`.../models/XXXXXXXXX/`）に直す                           |

> ⭐️ **40分枠では、同時アップロードの集中が最大のリスクです。** 3章の開始時刻を列ごとに1〜2分ずらす運用も検討してください。

## 8.3 ブロック台本の編集

もっとも個別フォローが集中する区間です。前方のスクリーンに、
4.3のJSON・4.4の表の記入例・4.5のJSONを**出し続けてください**。

| 症状                                          | 確認する場所                                                                           |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| `must be string`、`/assets/...`のSchemaエラー | assetの`VALUE`。名前で包んでいないか、`url`が`source`の内側か、`delivery: remote`があるか |
| 全角の引用符を入力した                        | `"`を半角に直す。日本語入力をオフにさせる                                              |
| `Unknown reference`、`Unknown actor`          | 衣装名の綴り。配布資料`suitors`のファイル名と参加者向け資料2.1の表を突き合わせる        |
| `recognitionModel`の指定が必要                | pose命令を含む`scene`自身の`PROPERTIES`                                               |
| 読み込みは終わるが次へ進まない                | `STEPS`の`pose`とモデルのクラス名の一致。`kime`の綴りを確認                            |
| 一覧フォームの入力が消えた                    | 「キャンセル」を押している。再入力して「保存」を押させる                               |
| 見本の行を消してしまった                      | 完成見本のSB3から該当行をコピーする、または1行だけで続行する                           |

よくある綴りミスは次の3つです。巡回時にここを見てください。

1. クラス名が`Kime`（大文字始まり）になっている → `kime`
2. モデルURLの末尾の`/`がない
3. 衣装名が`Umakai`（`Stand`／`Kime`が付いていない）

## 8.4 再生・動作確認

| 症状                             | 対処                                                           |
| -------------------------------- | -------------------------------------------------------------- |
| カメラ許可を拒否してしまった     | ブラウザのサイト設定からカメラを許可し、再読み込み             |
| モデルの読み込みで止まる         | ネットワークを確認。数秒待つ。`loading: lazy`なので場面到達後に読み込む |
| 認識が始まらない                 | `scene`の`recognitionModel`指定を確認（8.3）                   |
| 認識バーが動くがチャージが増えない | 同じポーズを維持させる。ポーズが揺れている                     |

## 8.5 救済手順（間に合わない場合）

**モデルのアップロードができない／間に合わない場合**

1. スタッフが事前に作成・公開しておいた**救済用モデルのURL**を配布する
2. 救済用モデルのクラス名も`kime`／`neutral`にそろえておく
3. 救済用モデルの`kime`は、求婚者カタログの決めポーズのうち**汎用的な1種**（両手を前に差し出す形など）で学習させておく
4. 参加者には、そのポーズを取ってもらう

【要作成：救済用モデルのURL（スタッフ用、複数本用意）】

**台本の編集が間に合わない場合**

1. 完成見本（`tekona-complete-sample.sb3`）を開かせる
2. 4.3のモデルURLだけを自分のものに差し替えさせる（1か所の編集で動く）
3. 一覧への行追加は省略し、見本の求婚者で再生する

> ⭐️ 救済手順に入ったことを、参加者に「失敗」と受け取らせないでください。「別の進め方に切り替える」と伝えてください。

# 9. 撤収作業内容

1. 教室内に忘れ物がないか確認し、回収する
2. 参加者のPCで、Teachable Machineのタブを閉じる（カメラ解放）
3. ブラウザの履歴・ダウンロードフォルダ・デスクトップの「tekona」フォルダを削除し、ごみ箱を空にする
4. 【要確定：アカウント方式】に応じたサインアウト処理を行う
5. PCをシャットダウンする
6. USBカメラを取り外し、台数を確認して所定の場所へ戻す
7. ディスプレイの向きを元に戻す
8. ワークシートの回収有無を確認する（アンケートと合わせて回収する場合）

> ⭐️ 参加者がTeachable Machineにアップロードしたモデルは、クラウド上に残ります。URLを知らなければ到達できませんが、**撤収時に削除する手段はありません**。参加者向け資料3.6で、URLに個人情報と映像が含まれないことを説明しています。

## 10.3 技術的に検証が必要な項目

1. **`forEach`の型付き参照を衣装名に使えるか（Schema上は成立、実装側の確認が残る）**

   参加者向け資料4.4は、求婚者の一覧（`forEach`の`items`）に
   `stand`・`kime`・`rejected`（衣装名）、`words`（セリフ）、`gift`（真偽値）の列を置き、
   アクション側から`{ref: suitor.stand}`のように参照する設計です。

   リポジトリ内のSchemaスナップショット2本
   （`sources/dsl4/dsl-4-narrative-control.schema.json`、`sources/dsl4/dsl-4.schema.json`）に対して
   ajvで検証したところ、次の結果でした。

   | 検証した内容                                                                     | 結果                 |
   | -------------------------------------------------------------------------------- | -------------------- |
   | `show.skin`・`pose.steps[].skin`・`setSkin.skin`・`say.text`・`if.condition`に`{ref: …}`を置いた`forEach`を、物語構造Schemaで検証 | **妥当**             |
   | 参照を行の値へ解決した後の通常アクションを、4.0 Schemaで検証                     | **妥当**             |
   | 参照を解決せずに残した通常アクションを、4.0 Schemaで検証                         | **不当**（解決が前提） |

   根拠は次の3点です。

   * 物語構造Schemaは通常アクションの中身を検査しません（`action`の最後の分岐が
     `additionalProperties: {}`）。そのため`{ref: …}`を置いても構造検証は通ります。
   * 同Schemaの`description`が「ordinary actions are validated using dsl-4.schema.json
     **after typed reference resolution**」と宣言しています。つまり参照解決が4.0検証より先です。
   * 解決後の値の型が合います。`skin`（`assetId`）は`literalId`＝1文字以上の文字列、
     `pose`（`id`）は`^[\p{L}_][\p{L}\p{N}_-]*$`です。`UmakaiStand`や`kime`は両方を満たします。
     `forEach`の行の値は文字列・数値・真偽値だけなので、ここに収まります。

   **設計上の重要な前提**：アクションのキーにはアクター名が埋め込まれます
   （`showAction`は`^[\p{L}_][\p{L}\p{N}_-]*\.show$`にマッチするキーを要求します）。
   キーに型付き参照は書けないため、**求婚者は1つのスプライト（`求婚者`）に統一し、
   カタログ8人分の衣装24枚をそのスプライトに登録します。**
   行ごとに変わるのは値だけになり、キーは`求婚者.show`・`求婚者.pose`のまま固定されます。
   求婚者ごとに別スプライトを立てる設計にすると、`forEach`では書けません。

   **ポーズのクラス名には型付き参照が不要です。** 全員のモデルで`kime`／`neutral`に
   統一しているため、`pose`は`kime`の固定値です。参照が必要なのは衣装名・セリフ・`gift`だけです。

   **残る確認事項**：参照解決がネストした値（`steps[].skin`など）まで及ぶかは、
   Appのランタイム実装側の問題で、このリポジトリのSchemaでは決まりません。
   上記の検証3は、解決されずに残った参照が4.0検証で落ちることを示しています。
   つまり**ネストまで解決されなければ、`skin`を指す検証エラーになります**。
   対応版CLIの`validate-dsl4`にベースSB3の台本を通して確認してください。

   解決が`say.text`などに限られていた場合の代替案：

   * **方式A（確実・個人作業向け）**：参加者1人につき1つの`scene`を用意し、
     衣装名とセリフを直接入力させる。`forEach`は使わない。
     参加者向け資料4.4を「シーン内の3か所を書き換える」手順に差し替える。
   * **方式B（一覧を活かす）**：`forEach`の一覧は`words`と`gift`だけに使い、
     衣装名は`scene`側に直接書く。

   方式Aは40分枠でも成立しますが、「一覧に1行足せば人物が増える」という
   データとプログラムの分離の体験が弱くなります。
   **確認結果によって、参加者向け資料4.4と6.1の記述が変わります。**

2. **全員分の求婚者を1つの一覧に連結した場合の上限**

   `forEach`の一覧は最大1024行、シーン1024／作品4096アクションの上限があります。
   参加者20〜40人規模であれば問題ありませんが、各行の展開アクション数と合わせて確認してください。

3. **複数の`recognitionModel`を1作品で扱う場合の挙動**

   6.1の連結再生では、参加者ごとに異なるモデルを場面ごとに切り替えます。
   `loading: lazy`で場面直前に読み込む設計ですが、
   **人数分のモデル切り替えが実時間で成立するかは未検証です。**
   成立しない場合は、連結再生を数人ずつのグループに分けてください。

4. **対応版の固定**

   物語制御（`if`／`repeat`／`forEach`／型付き参照）はApp 4.0.0-rc.44以降のStandardで利用できます。
   現在の公開版は4.0.1です。ベースSB3・CLI・埋め込みランタイムを同じ公開版へそろえてください。
