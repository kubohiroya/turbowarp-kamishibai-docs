# 1. ワークショップの概要

## 1.1 基本情報

| 項目       | 内容                                                       |
| ---------- | ---------------------------------------------------------- |
| 題材       | 真間の手児奈（市川市国府台・真間地域の伝説、『万葉集』）   |
| 対象       | 高校生                                                     |
| 所要時間   | 40分（休憩なし）                                           |
| 参加単位   | 2人1組、1人1台                                             |
| 開催日     | 【要確定】                                                 |
| 会場       | 【要確定】                                                 |
| 定員       | 【要確定】                                                 |
| 使用DSL    | DSL 4.0系（ブロック台本）【要確定：対応版、10.3を参照】    |

## 1.2 到達目標

参加者が40分で到達する状態を、次のとおり設定します。

1. 自分のポーズを学習させた機械学習モデルを作り、クラウドに公開できた
2. 公開したモデルのURLを、別のアプリ（紙芝居）の台本から参照できた
3. ブロック台本の決まった場所に、決まった形式でデータを入力し、作品を動かせた
4. エラー表示を読み、原因の箇所を特定して修正できた
5. 伝説を題材にした表現について、自分の考えを持てた

## 1.3 8月1日版（親子・小学生向け）からの変更点

40分枠に収めるため、次の変更を行っています。

| 観点             | 2026-08-01版                              | 本ワークショップ                                   |
| ---------------- | ----------------------------------------- | -------------------------------------------------- |
| 生成AIでの作画   | 実習に含む（約30分、保護者が操作）        | **実習から外す**（仮の絵のまま進め、差し替えは任意） |
| ポーズのクラス数 | 2〜4（`p1`〜`p4`）                        | **3固定**（`stand`／`kime`／`rejected`）           |
| 台本形式         | YAML台本（行頭の`#`を外す）               | ブロック台本（TurboWarp-Plus-Editor）              |
| 台本の編集量     | モデルURL・asset・action（3か所）         | 自分の席の枠だけ（モデルURL1か所、〔　〕の言葉7か所、`if`の条件1か所） |
| 休憩             | 10分                                      | なし                                               |
| 保護者の役割     | 生成AI操作、撮影オペレーター              | なし（2人1組で相互に撮影）                         |

> ⭐️ 生成AIでの作画を実習に戻す場合、40分では収まりません。最低90分枠が必要です。

> ⭐️ **モデルは参加者1人ずつが新しく作ります。** 席ごとに事前作成したモデルを配る運用ではありません。参加者が自分でクラウドへエクスポートし、台本の自分の枠のURLを書き換えます。ここが実習の中心です。

## 4.3 遅延時の切り詰め方

12分区間が押した場合、次の順で切り詰めます。

1. **5章の動作確認を省略**し、6.1の連結再生で自分の場面を見てもらう
2. **3.5のモデル確認を省略**し、Previewでのチェックをスタッフが代行する
3. **2章を短縮**し、言葉とポーズの説明を参加者向け資料の記入例のまま使わせる
4. **4.4の言葉の入力を省略**し、〔　〕のまま残して4.3のURLと4.5の条件だけを終わらせる

**切り詰めてはいけない箇所**

* 0.4の題材の扱い（全員が断られる設計の説明）
* 3.6のエクスポートURLの記録（ここを飛ばすと4章が成立しない）
* 4.3のモデルURLの書き換え（**この実習の中心**。ここを省略すると、自分のモデルで動かない）

# 6. 事前準備内容

1. PCの電源を入れる
2. USBカメラを接続し、認識を確認する
3. 【要確定：アカウント方式】に従ってログオンする
4. ログオン後に開く不要な画面を閉じる
5. エクスプローラーの「表示」→「ファイル名拡張子」にチェックを入れる
6. ブラウザを起動する
7. 配布URLからZIPファイルをダウンロードし、展開してデスクトップに「tekona」フォルダを配置する
8. 参加者向け資料PDFを開く
9. Teachable Machineのポーズプロジェクト（https://teachablemachine.withgoogle.com/train/pose ）を別タブで開いておく
10. 席番号（`01`〜`20`）の番号札を各席に貼り、割り当て表と突き合わせる
11. ベース作品（`tekona-workshop-blocks-4.0.sb3`）をTurboWarp-Plus-Editorで開く**リンクのタブ**を用意しておく（読み込みに時間がかかるため）
12. カメラの画角を確認し、着席した参加者の上半身が大きく映る向きに調整する
13. 背後に他の参加者が映り込まないか、実際に立って確認する
14. 完成見本（`tekona-complete-sample.sb3`）が再生できることを1台で確認する
15. **当日のネットワークで、Teachable Machineの「Upload my model」が通ることを確認する**
16. **1台で、スタッフが作ったモデルのURLを枠の`PoseNN`に書き換え、検証・保存して再生できることを確認する**（対応版が足りないと`Remote asset source does not match`で失敗します。10.3を参照）

> ⭐️ 手順15と16は、準備作業の中で最も重要です。アップロードが遮断される環境、またはURLの書き換えが通らない対応版では、このワークショップは成立しません。代替案は8.5を参照してください。

# 7. 高校生向けの進行上の注意

## 7.1 題材の扱い

手児奈の伝説は、**入水という結末を持つ物語**です。参加者向け資料0.4で扱いを明示していますが、
口頭でも冒頭に伝えてください。

* 伝説の結末を興味本位に強調しない
* 手児奈霊神堂が現在も信仰の場であることを伝える
* 伝説の人物を題材にした創作であることを明確にする

参加者から「なぜ死んでしまうのか」という質問が出た場合は、
『万葉集』に歌われた伝説としてそう伝えられている、と事実として答えてください。
解釈を断定せず、6.3の問いにつなげてください。

## 7.2 「断られる」体験のケア

この作品は、**設計上、全員の求婚者が断られます**。

* 開始時に、**全員が断られる設計であること**と、**その理由（伝説の筋書き）**を必ず先に伝える
* 「出来が悪いから断られた」と受け取る参加者がいないか、5章で表情を見る
* 断りのセリフに、個人を否定する表現を入れない（**参加者自身が書く欄**なので、巡回時に確認する）

参加者が考えた求婚の言葉が、相手を見下す内容・しつこく迫る内容になっていた場合は、
巡回時に書き直しを促してください。参加者向け資料2.1に注意書きがあります。

**手児奈の断りの言葉も、参加者自身が書きます。** 自分を強く否定する言葉になっていないか、
2章の巡回時と4.4の入力時に目を通してください。

## 7.3 カメラと肖像

* カメラ映像が保存されないことを明示する（参加者向け資料0.4・1.5）
* **他の参加者を撮影しない／画面を撮影してSNSに投稿しない**ことを冒頭で伝える
* カメラに他の参加者が映り込まない配置を、事前準備で担保する

## 7.4 生成AIについて

高校生は、M365 Copilotの利用対象年齢（13歳以上）を満たします。
ただし40分枠では画像生成を実習に含めないため、当日の生成AI操作は発生しません。
参加者の求婚者は、時間内は仮の絵のまま進めます（参加者向け資料4.7は、配布素材から選んで
差し替える任意作業です）。

発展課題として案内する場合は、次の点を伝えてください。

* 実在の人物に似せた画像を作らない
* 生成した画像の権利関係と、公開時の注意
* 生成結果が事実とは限らないこと

## 7.5 機械学習の説明の深さ

高校生向けなので、「例を見せると規則を見つける」という説明に加え、
次のどれかを**1分以内**で補足できると理解が深まります。参加者の反応を見て選んでください。

* `stand`クラスの役割（「それ以外」を教えないと何でも`kime`になる）
* サンプルを少し動かしながら撮る理由（学習データの多様性）
* 「Preview」での確認が、テストデータによる評価に相当すること

時間が押している場合は省略してかまいません。

# 8. トラブルシューティング

参加者の画面を確認し、作業がうまく進んでいない場合は声をかけ、スタッフが対応することを伝えてください。

## 8.1 Teachable Machineでの撮影・学習

| 症状                               | 対処                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------- |
| カメラが選べない／映らない         | ブラウザのカメラ許可を確認。複数カメラがある場合はプルダウンで切り替え |
| 上半身が小さく映る                 | カメラの位置を近づける。3クラスとも**同じ画角**で撮る                  |
| クラスが2つしかない                | 「Add a class」を1回押させる。クラス名は`stand`／`kime`／`rejected`    |
| どのポーズでも`stand`が高い        | `kime`・`rejected`のサンプルを追加し、形をもっと大きくして再トレーニング |
| `stand`と`rejected`が混ざる        | `rejected`はうつむく角度を深くして撮り直す                             |
| `kime`が上がらない                 | `kime`をより大きな形に変更し、撮り直す                                 |
| トレーニングが終わらない           | タブを切り替えていないか確認。切り替えていた場合は再トレーニング        |
| 他の参加者が映り込んで学習した     | 映り込んだ側のサンプルを削除し、画角を直して撮り直す                   |

## 8.2 モデルのエクスポート

| 症状                                   | 対処                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------- |
| 「Upload my model」が終わらない        | ネットワーク混雑。1〜2分待つ。繰り返す場合は8.5の救済へ                    |
| URLをメモし忘れてタブを閉じた          | タブが残っていれば「Export Model」から再コピー。閉じていれば8.5の救済へ    |
| URLの末尾の`/`が抜けている             | 末尾に`/`を付ける。参加者向け資料3.6の注意書きを示す                       |
| `model.json`のURLを控えてしまった      | ディレクトリURL（`.../models/XXXXXXXXX/`）に直す                           |

> ⭐️ **40分枠では、同時アップロードの集中が最大のリスクです。** 3章の開始時刻を列ごとに1〜2分ずらす運用も検討してください。

## 8.3 ブロック台本の編集

もっとも個別フォローが集中する区間です。前方のスクリーンに、
4.3のJSONの正しい入力例と、4.5の条件の変更前後を**出し続けてください**。

| 症状                                          | 確認する場所                                                                           |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| `must be string`、`/assets/...`のSchemaエラー | `asset PoseNN`の`VALUE`。`url`が`source`の内側か、`kind`／`delivery`／`loading`を消していないか |
| 全角の引用符を入力した                        | `"`を半角に直す。日本語入力をオフにさせる                                              |
| `Remote asset source does not match`          | **Appの対応版が足りない**。URLの書き換えを受け付ける版かを確認する（10.3）              |
| `Unknown reference`、`Unknown actor`          | コスチューム名。`stand`／`kime`／`rejected`から変えていないか（4.7の任意作業で起きやすい） |
| 読み込みは終わるが次へ進まない                | `STEPS`の`pose`とモデルのクラス名の一致。`kime`・`rejected`の綴りを確認                 |
| 自分の場面が再生されない                      | 4.5の`if`の条件。`false`のままになっていないか                                         |
| 他の人の枠を編集している                      | 席番号。番号札と`suitor-NN`・`SuitorNN`・`PoseNN`の`NN`を突き合わせる                   |
| 〔　〕が残っている状態で保存した              | 再生はできる。時間があれば4.4を続け、なければそのままにする                            |

よくある間違いは次の4つです。巡回時にここを見てください。

1. クラス名が`Kime`（大文字始まり）になっている → `kime`
2. モデルURLの末尾の`/`がない
3. 自分の席番号と違う枠を編集している
4. URLを`VALUE`の全体と置き換えてしまい、JSONの形がこわれている

## 8.4 再生・動作確認

| 症状                             | 対処                                                           |
| -------------------------------- | -------------------------------------------------------------- |
| カメラ許可を拒否してしまった     | ブラウザのサイト設定からカメラを許可し、再読み込み             |
| モデルの読み込みで止まる         | ネットワークを確認。数秒待つ。`loading: lazy`なので場面到達後に読み込む |
| 認識が始まらない                 | モデルURLとクラス名を確認（8.3）。枠の`recognitionModel`は設定済み |
| 認識バーが動くがチャージが増えない | 同じポーズを維持させる。ポーズが揺れている                     |

## 8.5 救済手順（間に合わない場合）

**モデルのアップロードができない／間に合わない場合**

1. スタッフが事前に作成・公開しておいた**救済用モデルのURL**を配布する
2. 救済用モデルのクラス名も`stand`／`kime`／`rejected`にそろえておく
3. 救済用モデルの`kime`・`rejected`は、**汎用的な1種**（両手を前に差し出す形、肩を落としてうつむく形）で学習させておく
4. 参加者には、そのポーズを取ってもらう

【要作成：救済用モデルのURL（スタッフ用、複数本用意）】

**台本の編集が間に合わない場合**

1. 4.3のモデルURLと4.5の`if`の条件だけを終わらせる（この2か所で自分のモデルで動く）
2. 〔　〕の言葉は仮のまま残してよい
3. それも間に合わない場合は、完成見本（`tekona-complete-sample.sb3`）を開かせ、用意済みの求婚者で再生する

**URLの書き換えを受け付ける対応版が間に合わない場合**

1. 参加者が作ったモデルのURLをワークシートから集める
2. Samples側の`workshop.config.json`の席ごとのモデルURL（`slotModelUrls`）に入れて、ベース作品を作り直す
3. 当日は、席ごとのモデルが埋まった作品を配り、参加者は言葉と`if`の条件だけを編集する

> ⭐️ この運用に切り替えると、**参加者が自分でURLを書き換える体験がなくなります**。10.3の確認結果によっては、ワークショップの組み立て直しが必要です。開催日の2週間前までに判定してください。

> ⭐️ 救済手順に入ったことを、参加者に「失敗」と受け取らせないでください。「別の進め方に切り替える」と伝えてください。

## 10.3 技術的に検証が必要な項目

1. **参加者がモデルのURLを書き換えられる対応版（最重要）**

   参加者向け資料4.3は、自分の枠の`asset PoseNN`の`source.url`を、自分がエクスポートした
   モデルのURLへ書き換える手順です。**この1か所がこの実習の中心**です。

   公開済みのAppは、作品に記録された素材の取得元と編集後のURLを突き合わせ、
   一致しない場合は`Remote asset source does not match: PoseNN`で読み込みを拒否します。
   半完成の作品で素材のURLを編集できるようにする修正は、App側のmainへ取り込まれています
   （kubohiroya/turbowarp-kamishibai-app#1184、PR #1185）が、
   **その版はまだ公開されていません**。公開されるまで、参加者がURLを書き換える手順は成立しません。

   | 確認すること | 判定方法 |
   | --- | --- |
   | 対応版が公開されているか | Appの公開Releaseの版番号を確認する（未公開のmain・作業ブランチは使わない） |
   | 公開版でURLの書き換えが通るか | 6の手順16を1台で実施し、検証・保存と再生まで通す |
   | Samplesのベース作品がその版で生成されているか | Samples側の`app-release.json`の版と、生成記録を突き合わせる |

   **開催日までに公開されない場合は、8.5の「URLの書き換えを受け付ける対応版が間に合わない場合」
   の運用に切り替えます。** その場合、参加者が自分でURLを書き換える体験はなくなります。
   1.1の「使用DSL」と参加者向け資料4.3の記述も変わるため、開催日の2週間前までに判定してください。

2. **用意済み求婚者の一覧（`forEach`）の型付き参照（ベース作品側の設計）**

   参加者の枠は`forEach`を使いません。席ごとに場面`suitor-NN`を並べる設計です。
   `forEach`を使うのは、**物語に最初から登場する8人の求婚者**の部分だけで、
   これはベース作品側の作り方の問題です。

   リポジトリ内のSchemaスナップショット2本
   （`sources/dsl4/dsl-4-narrative-control.schema.json`、`sources/dsl4/dsl-4.schema.json`）に対して
   ajvで検証したところ、次の結果でした。

   | 検証した内容                                                                     | 結果                 |
   | -------------------------------------------------------------------------------- | -------------------- |
   | `show.skin`・`pose.steps[].skin`・`setSkin.skin`・`say.text`・`if.condition`に`{ref: …}`を置いた`forEach`を、物語構造Schemaで検証 | **妥当**             |
   | 参照を行の値へ解決した後の通常アクションを、4.0 Schemaで検証                     | **妥当**             |
   | 参照を解決せずに残した通常アクションを、4.0 Schemaで検証                         | **不当**（解決が前提） |

   根拠は次の3点です。

   * 物語構造Schemaは通常アクションの中身を検査しません（`action`の最後の分岐が
     `additionalProperties: {}`）。そのため`{ref: …}`を置いても構造検証は通ります。
   * 同Schemaの`description`が「ordinary actions are validated using dsl-4.schema.json
     **after typed reference resolution**」と宣言しています。つまり参照解決が4.0検証より先です。
   * 解決後の値の型が合います。`skin`（`assetId`）は`literalId`＝1文字以上の文字列、
     `pose`（`id`）は`^[\p{L}_][\p{L}\p{N}_-]*$`です。`UmakaiStand`や`kime`は両方を満たします。
     `forEach`の行の値は文字列・数値・真偽値だけなので、ここに収まります。

   **設計上の前提**：アクションのキーにはアクター名が埋め込まれます
   （`showAction`は`^[\p{L}_][\p{L}\p{N}_-]*\.show$`にマッチするキーを要求します）。
   キーに型付き参照は書けないため、**用意済みの8人は1つのスプライトに統一し、
   24枚の衣装をそのスプライトに登録します。** 参加者の枠は席ごとに別スプライト
   （`SuitorNN`）なので、この制約の外にあります。

   **残る確認事項**：参照解決がネストした値（`steps[].skin`など）まで及ぶかは、
   Appのランタイム実装側の問題で、このリポジトリのSchemaでは決まりません。
   対応版CLIの`validate-dsl4`にベースSB3の台本を通して確認してください。
   成立しない場合は、用意済みの8人も席の枠と同じように場面を並べる書き方へ変更します。
   **参加者向け資料の手順は、この結果によって変わりません。**

3. **席の枠を人数分並べた場合の上限**

   シーン1024／作品4096アクションの上限があります。現在の枠は20席です。
   定員を増やす場合は、1席あたりの展開アクション数と合わせて確認してください。

4. **複数の`recognitionModel`を1作品で扱う場合の挙動**

   6.1の連結再生では、席ごとに異なるモデルを場面ごとに切り替えます。
   `loading: lazy`で場面直前に読み込む設計ですが、
   **人数分のモデル切り替えが実時間で成立するかは未検証です。**
   成立しない場合は、連結再生を数人ずつのグループに分けてください。

5. **対応版の固定**

   物語制御（`if`／`repeat`／`forEach`／型付き参照）はApp 4.0.0-rc.44以降のStandardで利用できます。
   ただし参加者がURLを書き換える手順には、項目1の対応版が必要です。
   ベースSB3・CLI・埋め込みランタイムは、**同じ公開版**へそろえてください
   （Samples側の`app-release.json`が正本です）。未公開の版を固定先に選ばないでください。
